Position at a glance

Five numbers that frame the renewal conversation. The headline: across all Tier 1 attributes, the best non-premium source would have sufficed for 94.6% of the universe, and the premium source is the sole provider for 3.1% of critical values.

How to read this pack

Every metric is computed against your in-scope universe (42,000 entities), not the vendor's delivered file, and evaluated as-of T+SLA so latency is never misread as inaccuracy. Sufficiency means the vendor's value matched the golden value within a per-attribute tolerance — it answers "would this have done?". Solo rate means no other licensed source held a valid value — it answers "what is this vendor uniquely worth?".

The renewal number

Marginal uplift = quality of the full five-source stack minus quality of the stack without that source. It reframes "Bloomberg is the best" into "Bloomberg adds X quality points over the next-best bundle, at $Y per point." Take that into the negotiation, not the raw ranking.

Decision rule

A source with solo rate ≈ 0 on all tiers, high sufficiency, and high pairwise overlap is redundant — it is negotiating leverage, not a dependency. A source holding a high solo rate on Tier 1 attributes is a dependency and should be retained, but you can still argue the price on the strength of the other 96% of its volume.

05

Data quality dimensions by source

The six dimensions, aggregated across attributes and weighted by field tier. Report this alongside sufficiency: a source can agree with the winner and still be slow, unstable, or badly formatted.

Agreement is not correctness

Two sources can share a common upstream provider and agree on the same wrong value. Watch for correlated error: when two sources disagree with the rest of the field in the same direction on the same records at the same time, treat it as one common-cause defect — not two independent ones — and raise it with both vendors simultaneously.

06

Implementation — Postgres OLTP + Iceberg + StarRocks

A three-tier architecture: PostgreSQL alpha holds golden records, tolerance rules, and steward overrides; bulk raw feeds reside in Apache Iceberg Parquet files (Lakekeeper); and StarRocks acts as the hot vectorized engine querying across both.

1. PostgreSQL alpha — OLTP Master Values, Rules & OverridesPort 5432
-- Golden master records, tolerances, and steward overrides live in Postgres OLTP
CREATE TABLE mdm_eval.golden_value (
    tenant_id          UUID        NOT NULL,
    as_of_ts           TIMESTAMP   NOT NULL,
    entity_id          BIGINT      NOT NULL,
    attribute_code     VARCHAR(64) NOT NULL,
    golden_value       TEXT,
    winning_vendor_id  UUID        NOT NULL,
    rule_applied       VARCHAR(64) NOT NULL,
    PRIMARY KEY (tenant_id, as_of_ts, entity_id, attribute_code)
);

CREATE TABLE mdm_eval.attribute_tolerance (
    attribute_code     VARCHAR(64) PRIMARY KEY,
    tier               SMALLINT    NOT NULL,      -- 1 = trade/compliance blocking
    match_type         VARCHAR(24) NOT NULL,      -- EXACT | FUZZY | NUMERIC_BP | DATE_LAG
    tolerance_val      NUMERIC,                    -- basis points, %, Jaro-Winkler cut-off
    tier_weight        NUMERIC(3,2) NOT NULL
);

CREATE TABLE mdm_eval.value_override (
    override_id        BIGSERIAL   PRIMARY KEY,
    entity_id          BIGINT      NOT NULL,
    attribute_code     VARCHAR(64) NOT NULL,
    prior_golden_value TEXT,
    prior_vendor_id    UUID,
    overridden_value   TEXT        NOT NULL,
    endorsement_vendor_id UUID,                    -- which vendor had the correct value
    defect_reason      VARCHAR(128),
    steward_id         VARCHAR(64),
    override_ts        TIMESTAMP   NOT NULL DEFAULT NOW()
);
2. Apache Iceberg (Lakekeeper) — Bulk Raw Feeds (Parquet)Port 8182 / S3
-- Non-surviving and raw vendor feeds pushed to Parquet / Iceberg (zero Postgres bloat)
CREATE TABLE raw_market_data.source_attribute_value (
    tenant_id          STRING,
    entity_id          BIGINT,
    attribute_code     STRING,
    vendor_id          STRING,
    raw_value          STRING,
    normalized_value   STRING,
    as_of_date         DATE,
    as_of_ts           TIMESTAMP,
    format_ok          BOOLEAN,
    range_ok           BOOLEAN,
    ref_integrity_ok   BOOLEAN
)
USING iceberg
PARTITIONED BY (as_of_date, vendor_id)
TBLPROPERTIES ('write.format.default'='parquet', 'write.parquet.compression-codec'='zstd');
3. StarRocks Hot Engine — Federated Vectorized EvaluationFE Port 9030
-- Mount Iceberg REST and Postgres alpha JDBC directly inside StarRocks:
CREATE EXTERNAL CATALOG lakekeeper_iceberg PROPERTIES (
    "type" = "iceberg", "iceberg.catalog.type" = "rest",
    "iceberg.catalog.uri" = "http://100.84.50.65:8182/v1"
);

CREATE EXTERNAL CATALOG pg_alpha PROPERTIES (
    "type" = "jdbc", "user" = "postgres", "password" = "postgres",
    "jdbc_uri" = "jdbc:postgresql://100.84.50.65:5432/alpha"
);

-- High-speed Vectorized Substitution & Solo Rate Evaluation (< 50ms):
WITH eval_states AS (
  SELECT s.attribute_code, s.vendor_id, s.entity_id, t.tier,
         CASE
           WHEN s.normalized_value IS NULL THEN 'ABSENT'
           WHEN NOT (s.format_ok AND s.range_ok AND s.ref_integrity_ok) THEN 'INVALID'
           WHEN (
             (t.match_type = 'EXACT' AND LOWER(TRIM(s.normalized_value)) = LOWER(TRIM(g.golden_value)))
             OR (t.match_type = 'NUMERIC_BP' AND ABS(CAST(s.normalized_value AS DOUBLE) - CAST(g.golden_value AS DOUBLE)) <= t.tolerance_val)
             OR (t.match_type = 'FUZZY_JARO' AND jaro_winkler_similarity(s.normalized_value, g.golden_value) >= t.tolerance_val)
           ) THEN 'VALID_MATCH'
           ELSE 'VALID_DIFFERS'
         END AS eval_state
  FROM      lakekeeper_iceberg.raw_market_data.source_attribute_value s
  JOIN      pg_alpha.mdm_eval.golden_value g 
            ON g.entity_id = s.entity_id AND g.attribute_code = s.attribute_code AND CAST(g.as_of_ts AS DATE) = s.as_of_date
  JOIN      pg_alpha.mdm_eval.attribute_tolerance t ON t.attribute_code = s.attribute_code
  WHERE     s.as_of_date = CURRENT_DATE()
)
SELECT attribute_code, vendor_id, tier,
       COUNT(*) AS in_scope,
       ROUND(100.0 * COUNT(CASE WHEN eval_state = 'VALID_MATCH' THEN 1 END) / COUNT(*), 2) AS substitution_rate_pct
FROM eval_states
GROUP BY attribute_code, vendor_id, tier
ORDER BY tier, substitution_rate_pct DESC;
Methodology notes

Match tolerances are held in attribute_tolerance, never in code, so a tolerance change can be re-run historically. Identifiers match exact; names use Jaro-Winkler ≥ 0.92; prices within 1 basis point after rounding normalisation; numerics within 0.01% relative; dates exact or ±1 business day where the semantic is as-of.

Composite index = 0.30 coverage + 0.25 accuracy + 0.15 validity + 0.15 timeliness + 0.10 consistency + 0.05 stability, aggregated with tier weights 0.50 / 0.30 / 0.20.
